# CASA 7.2.1 / 7.2.2 — CardCom webhook: compensating, provider-specific control

**Status:** assessor-facing evidence memo · v1 · 2026-08-31
**Applies to:** CASA Specification v2.1.1 (2026-06-03), test cases **7.2.1** and **7.2.2**
**Subject:** the inbound CardCom payment webhook, `POST /api/payments/webhook/cardcom`

> **This memo does not claim HMAC signature verification, because none exists for this provider.** It describes a compensating, provider-specific control and asks the assessor to evaluate it as such.

---

## 1. What the requirement asks for

**7.2.1** — *"Webhook payloads shall be authenticated using HMAC-SHA256 (or stronger) cryptographic signature verification… Webhook consumers shall verify signatures against the raw request body before processing. Requests with missing, invalid, or mismatched signatures shall be rejected."* The requirement description additionally states that relying on endpoint obscurity or static API keys in headers is not sufficient.

**7.2.2** — *"Signature verification shall use timing-safe comparison functions."*

## 2. Why literal compliance is not attainable for this provider

Dubiz is a webhook **consumer**, not a provider. It consumes callbacks from exactly one live payment provider: **CardCom** (an Israeli payment gateway).

**CardCom publishes no webhook signing mechanism.** Its documented model for the LowProfile flow is:

1. the merchant registers a `WebHookUrl` when creating a LowProfile payment session;
2. CardCom calls that URL carrying a `LowProfileId` and any `ReturnValue` the merchant supplied at creation;
3. the merchant establishes what actually happened by calling **`/api/v11/LowProfile/GetLpResult`** server-to-server, authenticating with its own terminal number and API credentials.

There is no signature header, no signing secret, and no published payload MAC. **No implementation on our side can produce a signature the provider does not send.** Any claim of HMAC verification for this endpoint would be false.

**We removed a control that pretended otherwise.** A previous implementation defined a `CARDCOM_WEBHOOK_SECRET` environment variable and looked for an `x-cardcom-secret` header. That control was defective twice over: the header is one CardCom never sends (so configuring the secret would have rejected every legitimate callback and broken settlement), and when the variable was unset — its state in every environment — the verifier returned `ok`, i.e. it **failed open**. It was deleted rather than repaired, because a shared secret invented by the consumer is not provider authentication and presenting it as such would misstate the control.

**7.2.2 is not applicable in isolation for this provider**: there is no signature to compare, therefore no comparison to make timing-safe. Where a signature does exist in this codebase — the Meta/WhatsApp webhook, `X-Hub-Signature-256` — it is verified as HMAC-SHA256 over the **raw request body** using `crypto.timingSafeEqual`, and is offered as the reference implementation of both test cases.

## 3. The compensating control

Authenticity is established by a chain in which **the callback is never authoritative**. Every step is fail-closed.

| # | Gate | What it establishes | Failure |
|---|---|---|---|
| 1 | **Structural** | The body is a well-formed CardCom LowProfile callback carrying a canonically-shaped `LowProfileId` (GUID). | Refused |
| 2 | **Correlation** | The `LowProfileId` must resolve, through an internal routing index, to a `PaymentRequest` **this system created**. The identifier is generated by CardCom at LowProfile/Create in response to *our* authenticated request and stored by us; it is not guessable and not public. | Refused |
| 3 | **Second correlation channel** | `ReturnValue` — which we set to our own `PaymentRequest.id` at creation and CardCom round-trips — must equal the id of the request that step 2 resolved to. A caller must therefore reproduce **two** values this system generated, and a real identifier observed in one payment flow cannot be pointed at another. | Refused |
| 4 | **Coherence** | Any amount or currency the body claims must match the stored request. | Refused |
| 5 | **Tenant derivation** | The owning business is taken from the **stored** `PaymentRequest`, never from the payload. The routing index is treated as a hint and the request is re-read under both the routed id and the routed business id, so a mismatch yields nothing. | Refused |
| 6 | **Authority** | Only now does anything settle — and the outcome comes **exclusively** from an authenticated server-to-server `GetLpResult` call made with the tenant's own CardCom credentials. The outcome asserted by the callback body is ignored entirely; the parser cannot even emit `PAID`. A failed or erroring verification can never produce `PAID`. | Never `PAID` |
| 7 | **Idempotency** | Database-level uniqueness on `(provider, providerEventId)` for the event and on `(provider, providerTransactionId)` for the settlement; a terminal request status is never overwritten; the downstream financial projection is keyed on the transaction id. | Settles once |

**Nothing is persisted until step 5 passes.** Steps 1–4 run before any database write, so a caller who cannot reproduce identifiers this system issued leaves no row behind and triggers no outbound provider call. This closes the practical abuse of an unauthenticated public endpoint: unbounded writes and unbounded forced lookups.

**A forged callback therefore cannot:** create or alter a payment, produce a `PAID` state, create a `PaymentTransaction`, emit a `FinancialEvent`, cross a tenant boundary, or persist anything at all.

**Deliberate response behaviour.** The endpoint answers `200` even when it refuses. This prevents provider retry storms and, more importantly, denies an enumeration oracle — a caller cannot use the status code to learn whether a `LowProfileId` is real. Refusals are logged.

## 4. Evidence available for review

- **Code:** `lib/services/payments/providers/cardcom/cardcom.provider.ts` (`verifyWebhook`, `parseWebhook`, `getPaymentStatus`), `lib/services/payments/payment-webhook.service.ts` (the ordered chain above).
- **Adversarial test suite:** `lib/services/payments/cardcom-webhook-hardening.test.ts` — nine scenarios: legitimate settlement; random identifiers; missing/malformed fields; verification-says-declined; `ReturnValue` mismatch; cross-business identifier reuse; duplicate callback; repeated settlement under a different event envelope; unconfigured provider. Each asserts both the refusal **and** the absence of any database mutation.
- **Regression protection:** the suite runs in the repository's **blocking** CI job, with two negative proofs that re-plant real defects (a restored provider fail-open, and a dropped correlation check) and require the suite to catch them.
- **Reference compliant implementation:** `lib/services/integrations/whatsapp/webhook-verify.service.ts` — HMAC-SHA256 over the raw body with `timingSafeEqual`, offered as evidence that the codebase implements 7.2.1/7.2.2 properly wherever a provider makes it possible.

## 5. What we are asking the assessor to decide

Whether, for a webhook provider that publishes no signing mechanism, the chain in §3 is accepted as a compensating control for 7.2.1, and whether 7.2.2 is accepted as not applicable to that provider.

We have deliberately **not** substituted a self-invented shared secret to make the control *look* like signature verification. If the assessor's position is that 7.2.1 admits no compensating control, the alternative available to us is to descope payments for the certification period — the integration is in limited use — rather than to misrepresent the control.

## 6. Scope note

Two further payment providers exist in the codebase (**Tranzila**, **PayPal**) but are **dormant**: no active connection, no payment request, no configured credential in any environment. Both previously shared the same fail-open branch; both now refuse all callbacks while unconfigured. If PayPal is ever activated, its real mechanism — the `verify-webhook-signature` API with a registered webhook id — is what must be implemented, and 7.2.1 would then be satisfiable literally for that provider.
