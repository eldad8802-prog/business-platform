# קופונים — Plan לשלב 3 (יכולות חדשות + שינויי-מודל)

> **סטטוס (2026‑07‑07): Stage 3 סגור ללא C5.** אושרו **C4** (פופולריות + מסתיימים‑בקרוב, ללא schema), **C1+C2** (city/lat/long/openingHours — additive nullable, migration `20260707120000`), **C3** (מרחק server‑side + קרוב‑אליך + סינון‑עיר, ללא schema). **C5 נדחה** לדור ההנפקה הפר‑משתמש כדי לשמור על עוגן `couponId @unique` — ראה [C5 decision §0](./coupon-c5-quota-semantics-decision-v1.md). **נשמר:** מסתיימים‑בקרוב · פופולריות · מיקום/מרחק · עיר/שעות.
>
> **מה זה:** תוכנית ארכיטקטונית/טכנית לשלב 3 בלבד. **לא קוד · לא migration · לא שינוי schema.** מיפוי כדי להחליט איך להתקדם.
> **גבול:** שלב 3 = הפעם הראשונה שנוגעים ב-DB/מודל. שלב 4 (צרכן / QR-פר-משתמש / Affiliate / Marketplace מלא) נשאר בנפרד.
> **ממשל-migration מחייב (קיים בפרויקט):** רק **expand-only** (הוספות nullable, backward-compatible); פרודקשן רק דרך ה-workflow הגָדוּר `release-migrate`; DDL עם `DIRECT_URL`. כל שינוי שאינו-expand-only (הסרת-constraint/שינוי-סמנטיקה) = **דגל אדום**, טיפול נפרד.
> **בסיס:** המודל הקיים (BusinessProfile/Offer/Coupon/RedemptionEvent) + [reality-check](./coupon-design-vs-system-reality-check-v1.md).

## 1. אילו יכולות נדרשות (מלאי + תלויות)
| # | יכולת | מה במסך |
|---|---|---|

| **C3** | מרחק · "קרוב אליך" · סינון-עיר | תג-מרחק, שורת "קרוב אליך", filter עיר |

## 2. פירוט פר-יכולת

### C1 · מיקום מובנה (עיר + geo)
- **DB:** הוספת שדות nullable ל-`BusinessProfile`: `city String?`, `latitude Float?`, `longitude Float?` (אולי `region`). **expand-only ✅**.
- **API:** לחשוף `city` ב-`active`/`details` DTO; distance מחושב בנפרד (ראה C3).
- **השפעה על נתונים:** אין הרס. עסקים קיימים = null → אין עיר/geo עד מילוי. **Backfill** = geocoding מ-`billingAddress` או קלט-בעל-עסק.
- **סיכון:** נמוך למודל; דיוק/עלות geocoding בינוני.
- **החלטת מוצר:** (א) geocoding אוטומטי משירות חיצוני (תלות/עלות) מול קלט-ידני של בעל-העסק; (ב) עיר מובנית מול טקסט-חופשי.

### C2 · שעות פעילות
- **DB:** `businessHours` על `BusinessProfile` — `String?` (חד-שורתי "א׳–ה׳ 8:00–18:00") **או** `Json?` (מובנה פר-יום). **expand-only ✅**.
- **API:** לחשוף ב-`active`/`details`.
- **השפעה:** אין; null עד מילוי (קלט-בעל-עסק).
- **סיכון:** נמוך.
- **החלטת מוצר:** טקסט-חופשי (מספיק לעיצוב) מול מובנה (מאפשר "פתוח עכשיו" בעתיד).

### C3 · מרחק · "קרוב אליך" · סינון-עיר
- **DB:** אין חדש (מסתמך על C1).
- **API:** distance דורש **מיקום-צרכן**. שתי דרכים: (א) ה-API מקבל `?lat&lng` וממיין/מחשב מרחק שרת-צד; (ב) ה-API מחזיר geo והלקוח מחשב. סינון-עיר: `?city=` או סינון-לקוח.
- **השפעה:** אין; שורת "קרוב אליך" ריקה עד שיש geo לעסקים + הרשאת-מיקום.
- **סיכון:** UX של הרשאת-geolocation; דיוק; **הגברת חשיפה ציבורית** (geo של עסקים חשוף).
- **החלטת מוצר:** לבקש מיקום-דפדפן? fallback כשנדחה/חסר? חישוב שרת מול לקוח?

### C4 · פופולריות · "הכי מבוקשים"
- **DB (מינימלי):** **אין** — דירוג לפי ספירת `RedemptionEvent` per-offer (נגזר). **החיסכון הכי זול בשלב 3 — בלי schema.**
- **DB (מלא):** מוני-צפייה/תביעה (שדה/טבלה חדשים) — expand-only, אך כתיבה בכל צפייה ציבורית (scale).
- **API:** להוסיף מיון "popular" (param/endpoint) או קיבוץ-שורות.
- **השפעה:** אין; משמעותי רק כשיש מימושים.
- **סיכון:** נמוך (aggregate); מוני-צפייה = כתיבות תכופות (scale).
- **החלטת מוצר:** "מבוקש" = מימושים (זמין) מול צפיות/תביעות (מעקב חדש).

### C5 · מכסה/מלאי · "אזל" · qty bar  ⚠️ (הכבד ביותר)
- **הסתבכות-ליבה:** "X מתוך 50" תלוי במשמעות: **50 מימושים של קופון משותף** מול **50 הנפקות ייחודיות פר-משתמש**. השני = **שלב 4** (מודל-צרכן + QR-פר-משתמש). לכן C5 **שלוב עם שלב 4**.
- **DB:** `maxRedemptions`/`quota Int?` על `Offer`/`Coupon` (nullable=ללא-הגבלה, expand-only ✅) — אבל **"נותרו"** דורש ספירה. היום `RedemptionEvent.couponId @unique` (1:1) → **מימוש יחיד לקופון**. ריבוי-מימושים דורש **הסרת-ה-@unique + שינוי לוגיקת-redeem** = **לא-expand-only, דגל אדום**.
- **API:** `active`/`details` יחזירו `remaining = quota − count`; redeem/issue יאכפו תקרה; מצב "אזל".
- **השפעה על נתונים:** offers קיימים = ללא-מכסה. **שינוי סמנטיקת-המימוש** משפיע על מנגנון קיים (RISK).
- **סיכון:** **גבוה** — שינוי מודל-מימוש, מרוץ-מקביליות על "היחידה האחרונה", שינוי-constraint (לא-expand-only), שלוב עם שלב 4.
- **החלטת מוצר (קריטית):** משמעות המכסה (מימושים מול הנפקות). **המלצה: לדחות את C5 האמיתי לשלב 4** (שם מודל-ההנפקה מגדיר "הונפקו X מתוך 50" באופן טבעי), או להכריע במפורש סמנטיקה + לקבל את שינוי-המימוש.

### C6 · קיבוץ 3 שורות המרקטפלייס
- **DB:** אין (הרכבה של C3/C4/C5).
- **API:** endpoint מקובץ (3 מיונים) או החזרת-רשימה + קיבוץ-לקוח.
- **פירוק:** **near** ⟵ C1/C3 (geo). **popular** ⟵ C4 (נגזר, בלי schema). **"אוזלים במהרה"** ⟵ **expiry** (מיון לפי `expiresAt`, **בלי schema!**) — לא חייב את C5. הריבון "אזל" עצמו ⟵ C5.
- **סיכון:** נמוך.

## 3. חתך-רוחב

**ממשל-migration:** C1/C2 = הוספות nullable (expand-only, בטוח, דרך `release-migrate`). C5 (אם נוגע ב-`@unique`/סמנטיקת-מימוש) = **אינו expand-only** → לא לערבב עם השאר; לתכנן כשינוי נפרד וזהיר (או לממש כטבלה/שדה חדשים במקום לשנות את RedemptionEvent).

**פרטיות/חשיפה:** חשיפת עיר/geo/שעות + מרקטפלייס חוצה-עסקים ציבורי מגבירה את **חשיפת-ה-[U]** שסומנה. יש להכריע כוונת-פרסום **לפני** הוספת מיקום. שלוב עם מודל-הצרכן (שלב 4).

## 4. סדר מימוש מומלץ
1. **C4 (popular, נגזר) + C6-"soon" (לפי expiry)** — **בלי schema**, מדליק 2 מ-3 השורות מיד, סיכון נמוך.
2. **C1 + C2** — migration אחד expand-only (city/geo/hours nullable ל-BusinessProfile) + הכרעת-geocoding.
3. **C3** — מרחק/"קרוב אליך"/סינון-עיר (מסתמך על C1 + הכרעת מיקום-צרכן).
4. **C5** — אחרון, **גדוּר בהכרעת מודל-ההנפקה** (ייתכן שיעבור לשלב 4).

## 5. מה בבת-אחת ומה נפרד
- **יחד (בלי DB):** C4 + C6-"soon" — שכבת-API/frontend בלבד. אפשר קודם ובעצמאות.
- **יחד (migration אחד, expand-only):** C1 (city/geo) + C2 (hours) — עמודות nullable ל-BusinessProfile.
- **נפרד + עצמאי:** C3 (frontend/API + מיקום-צרכן) — אחרי ש-C1 נחת ויש geo.
- **נפרד + גָדוּר:** C5 (מכסה/"אזל") — אינו-expand-only פוטנציאלית; דורש הכרעה; לא לערבב.

## 6. החלטות-מוצר לפני מימוש (מרוכז)
1. **סמנטיקת-מכסה (C5):** מימושים-של-קופון-משותף מול הנפקות-ייחודיות-פר-משתמש → קובע אם C5 בשלב 3 או 4, והאם נוגעים במודל-המימוש. **(הקריטית ביותר.)**
2. **Geocoding (C1/C3):** אוטומטי-משירות-חיצוני מול קלט-ידני; עיר מובנית מול חופשית.
3. **מיקום-צרכן (C3):** לבקש geolocation? fallback? חישוב שרת מול לקוח?
4. **פורמט-שעות (C2):** טקסט-חופשי מול מובנה.
5. **הגדרת-פופולריות (C4):** מימושים מול צפיות/תביעות (מעקב חדש).
6. **פרטיות/חשיפה (חתך):** אישור כוונת-הפרסום הציבורי חוצה-העסקים לפני חשיפת מיקום — שלוב עם מודל-הצרכן.

## 7. תמצית-החלטה
- **מהיר (בלי schema, סיכון נמוך):** C4 popular + "אוזלים לפי-תוקף" → 2/3 שורות המרקטפלייס.
- **expand-only בטוח:** C1(city/geo)+C2(hours) ב-migration אחד → hero-מיקום + שעות + בסיס-מרחק.
- **דורש מיקום-צרכן:** C3 (מרחק/near/סינון-עיר).
- **דורש הכרעה גדולה + אולי שלב 4:** C5 (מכסה/"אזל"/qty) — אל תתחיל בלי הכרעת-סמנטיקה.
