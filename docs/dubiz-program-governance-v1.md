# Dubiz — Program Governance v1

> **מה זה:** חוקי העבודה של הפרויקט. איך תוכניות נפתחות, מתקדמות ונסגרות.
> **מה זה לא:** לא ארכיטקטורת קוד · לא מוצר · לא מתודולוגיה חיצונית. **אין כאן
> Scrum, SAFe או PMI.**
> **מקור:** הדרך שבה Dubiz כבר עובדת בפועל — מסמך לפני קוד, מזהי פער ניתנים
> לציטוט, שערים במקום אחוזים, וראיה במקום הצהרה. המסמך **מנסח** את זה, לא ממציא.
> **גרסה:** v1 · **תאריך:** 2026-08-18.

## 0. חמשת העקרונות

כל שאר המסמך נגזר מאלה. אם כלל סותר עיקרון — העיקרון גובר.

| # | העיקרון | המשמעות |
|---|---|---|
| **G1** | **ראיה, לא הצהרה** | "הסתיים" נאמר רק כשאפשר להראות. ללא ראיה — לא עובדה. *(הכלל שהאודיטים נבנו עליו.)* |
| **G2** | **מסמך לפני קוד; המסמך הוא הסמכות** | קוד שסותר מסמך מאושר — אחד מהם פגום, והפער נסגר לפני מיזוג |
| **G3** | **לכל פער בעלים אחד** | פער שייך לתוכנית אחת בלבד. שיתוף = גבול שגוי |
| **G4** | **סמכות יורדת, עובדות עולות** | ההיררכיה מכתיבה מלמעלה; מדידה מתקנת מלמטה |
| **G5** | **אין הצטברות** | תהליך רשאי להתחדד ולהתקצר, אסור לו להתנפח. חריגים שמצטברים הורגים ממשל |

## 1. היררכיית המסמכים

```
חוקה · זהות · שפה עיצובית        ← מה Dubiz היא (מוצר)
        ▼
Baseline + Release Audits         ← מה קיים במערכת (עובדות)
        ▼
Master Program Architecture       ← סדר הבנייה
        ▼
Program Design Documents          ← מה כל תוכנית עושה
        ▼
Work Packages                     ← יחידות עבודה
        ▼
Pull Requests                     ← השינוי בפועל
```

**שני כיווני זרימה:**
- **סמכות יורדת:** מסמך נמוך שסותר גבוה — **בטל בחלק הסותר**, מיידית.
- **עובדות עולות:** מדידה חדשה שסותרת את הבסיס **מעדכנת את הבסיס** (§7.3).

**כלל אי־כפילות:** עובדה נכתבת **במקום אחד**. מסמך אחר מצטט אותה במזהה, לא משכפל
אותה.

## 2. Program Lifecycle

```
Proposed ──► Designed ──► Open ──► Executing ──► Verifying ──► Closed
                                                                 │
                                                          Reopened ◄┘
```

| המצב | מה קורה בו | היציאה ממנו |
|---|---|---|
| **Proposed** | נטען שקיימת שכבת יסוד שחסרה | עומד במבחן §8.3 (תוכנית או חבילה?) |
| **Designed** | קיים Design Doc | **Entry Gate** (§3) |
| **Open** | בעלות נקבעה, תלויות סגורות | הוקצו חבילות עבודה |
| **Executing** | חבילות מתקדמות | כל החבילות סגורות |
| **Verifying** | הדגמת קריטריוני הקבלה | **Exit Gate** (§4) |
| **Closed** | הפערים סגורים, הבסיס מעודכן | — |
| **Reopened** | רק לפי §2.1 | חוזר ל-Executing |

### 2.1 פתיחה מחדש
תוכנית סגורה נפתחת מחדש **רק** כאשר: קריטריון קבלה שהודגם **חדל להתקיים**, או
**מדידה חדשה** מפריכה עובדה שעליה נשענה סגירתה.

**רצון, רעיון או שיפור אינם עילה לפתיחה מחדש.** הם פער חדש (§8) או חבילה
בתוכנית אחרת.

## 3. Entry Gate

תוכנית אינה נכנסת ל-Open לפני שכל שישה מתקיימים:

| # | התנאי | הכשל האופייני |
|---|---|---|
| **E1** | **Design Doc מאושר** — היקף, מטרות, ארכיטקטורה, מצב נוכחי ויעד | "נתחיל ונראה" |
| **E2** | **כל פער שויך בלעדית** ומצוטט במזהה | פער שמופיע בשתי תוכניות |
| **E3** | **תלויות סגורות או מוותרות במפורש בכתב** | הנחה שתלות "כמעט מוכנה" |
| **E4** | **קריטריוני קבלה ניתנים להדגמה** | "95% הושלם" |
| **E5** | **בעלים אחד נקוב** (אדם, לא צוות) | בעלות מפוזרת |
| **E6** | **התנגשויות עם תוכניות אחרות רשומות** — לאו דווקא פתורות | התנגשות שמתגלה בזמן מיזוג |

**E3 — כלל הוויתור:** מותר להתחיל לפני שתלות נסגרה, **בתנאי** שנכתב מה נבנה
זמנית ומה ייבנה מחדש. **ויתור שלא נכתב אינו ויתור — הוא חוב סמוי.**

## 4. Exit Gate

| # | התנאי |
|---|---|
| **X1** | **כל קריטריון קבלה הודגם** — לא הוצהר. עם ראיה שמישהו אחר יכול לשחזר |
| **X2** | **כל פער משויך נסגר**, או הועבר לתוכנית אחרת **עם נימוק כתוב** |
| **X3** | **אין פער שהתגלה במהלך העבודה ונשאר ללא בעלים** |
| **X4** | **הבסיס עודכן** בכל מקום שבו עובדה השתנתה (§7.3) |
| **X5** | **התנגשויות שנרשמו ב-E6 — נפתרו או הועברו** בכתב לתוכנית שתפתור אותן |

**אין סגירה חלקית. אין "סגור חוץ מ־".** תוכנית עם שארית פתוחה — פתוחה.

## 5. Work Packages

**חבילת עבודה** = יחידת עבודה בעלת מטרה אחת, גבולות מוצהרים, תוצרים ותנאי סיום.

| # | הכלל |
|---|---|
| **W1** | חבילה שייכת ל**תוכנית אחת בלבד**. |
| **W2** | **חבילה שנראית שייכת לשתיים — היא סימן לגבול תוכנית שגוי.** מפצלים או מעבירים; **לא משתפים.** |
| **W3** | לחבילה תנאי סיום משלה, שאינו "עבר קוד ריוויו" אלא **מה שאפשר להראות**. |
| **W4** | סדר בין חבילות הוא **תלות**, לא לוח זמנים. |
| **W5** | חבילה שאינה משרתת קריטריון קבלה של התוכנית — אינה שייכת אליה. |

## 6. Pull Requests

**עקרונות, לא תבנית.**

| # | הכלל |
|---|---|
| **P1** | כל PR מצהיר: **תוכנית · חבילה · מזהי הפער שהוא נוגע בהם · איזה קריטריון קבלה הוא מקדם.** |
| **P2** | **PR שאינו מצטט פער — אינו עבודה מאושרת**, אלא אם הוא תיקון תקלה דחוף (ואז הוא מייצר פער בדיעבד). |
| **P3** | **PR אינו מרחיב היקף בשקט.** עובדה חדשה → עוצרים ומדווחים (§7.2). |
| **P4** | PR שמשנה התנהגות מתועדת — **מעדכן את המסמך באותו PR**, או מצטט את התיקון שאישר זאת. |
| **P5** | PR שנוגע באזור חיכוך ידוע (§9.2) מציין זאת במפורש. |
| **P6** | **כל אחד רשאי לעצור PR בציטוט כלל או פער.** נטל ההוכחה על המציע, לא על העוצר. |

## 7. Architecture Changes ועקביות מסמך־קוד

### 7.1 מתי שינוי קוד מחייב שינוי מסמך

| הסוג | מחייב מסמך? |
|---|---|
| מימוש בתוך היקף מאושר | ❌ |
| שינוי חוזה בין רכיבים | ✅ Program Design |
| שינוי ברמת יסוד (זהות, תצורה, אירועים) | ✅ Design + Master |
| שינוי סדר בנייה או תלות | ✅ Master Program Architecture |
| **עובדה שנמדדה אחרת ממה שכתוב** | ✅ **Baseline** (§7.3) |
| שינוי בהתנהגות מוצר כלפי משתמש | ✅ החוקה/הזהות **תחילה** |

### 7.2 כלל "עצור והצג"

מי שמגלה במהלך העבודה עובדה שסותרת מסמך מאושר: **עוצר · מציג מה הבעיה, איפה
היא, למה לא התגלתה קודם, ומה ההצעה · ואז ממשיך.**

**זהו הכלל שכבר עובד בפרויקט בפועל, והוא הופך כאן למחייב.**

### 7.3 תיקון הבסיס

הבסיס מתוקן **רק במדידה**, לעולם לא בהערכה. תיקון מציין: **מה נמדד · מתי · מה
השתנה ביחס לגרסה הקודמת.** פריטי `UNVERIFIED` נסגרים **רק** בראיה, ולא בהסכמה.

## 8. Change Management

### 8.1 בקשה חדשה — שלוש שאלות בסדר הזה

1. **האם זו עובדה או רצון?** רצון אינו פער. פער מגיע ממדידה.
2. **האם הוא נופל בתוך מטרת תוכנית קיימת?** → חבילה חדשה שם.
3. **האם הוא **משנה** את מטרת התוכנית?** → זהו שינוי היקף (§8.2) או תוכנית חדשה (§8.3).

### 8.2 שינוי היקף
נרשם ב-Design Doc של התוכנית עם: מה נוסף/הוסר · למה · על אילו קריטריוני קבלה
זה משפיע · האם התלויות השתנו.
**שינוי היקף שאינו כתוב — לא קרה.**

### 8.3 מבחן התוכנית החדשה

תוכנית חדשה מוצדקת רק אם **כל** שלושת אלה מתקיימים:
1. היא בונה **שכבת יסוד**, לא יכולת בודדת.
2. **יותר מצרכן אחד** נשען עליה.
3. בנייתה בתוך תוכנית קיימת הייתה **מעוותת את מטרתה**.

**אחרת — זו חבילת עבודה.** *(שני התנאים הראשונים הם בדיוק הקריטריון שלפיו נבנו
שמונה התוכניות ב-Master Program Architecture.)*

## 9. Parallel Development

### 9.1 הסמכות
**מטריצת המקביליות ב-Master Program Architecture היא הסמכות.** ✅ בטוח ·
⚠️ בתיאום · ❌ אסור.

**ריצה מקבילה בניגוד למטריצה מחייבת ויתור כתוב לפי E3** — כולל הצהרה מה ייבנה
מחדש.

### 9.2 אזורי חיכוך
אזורי החיכוך שזוהו (F1–F5) הם **רשימה חיה**. כלל: **לאזור חיכוך יש בעלים אחד.**
תוכנית אחרת שנדרשת לגעת בו — **מבקשת, לא נוגעת.**

### 9.3 מניעת עבודה כפולה
**מרשם העבודה הוא מזהי הפער.** אין מזהה — אין עבודה. **פער אחד, בעלים אחד,
תוכנית אחת** (G3) — זהו המנגנון היחיד שמונע כפילות, ואין צורך באחר.

### 9.4 התנגשות בין תוכניות
נרשמת ב-E6 · **מסומנת ולא נפתרת** בתוך תוכנית שאינה בעליה · נפתרת בתוכנית שיש
לה הסמכות · **X5 חוסם סגירה** של תוכנית עם התנגשות פתוחה שלא הועברה.

## 10. Quality Gates

נגזרים מהמתודולוגיה שכבר הופעלה בפרויקט — לא מיובאים.

| # | השער | השאלה | חובה? |
|---|---|---|---|
| **Q1 · Design** | האם התכנון מאושר וההיקף חד? | **כל תוכנית** |
| **Q2 · Adversarial** | האם מישהו ניסה להפיל את זה בכוונה? | **מותנה** — ראו למטה |
| **Q3 · Implementation** | האם נבנה בתוך ההיקף, בלי דריפט חדש? | כל תוכנית |
| **Q4 · Verification** | האם הודגם — לא הוצהר? | כל תוכנית |
| **Q5 · Evidence** | האם קיים תיעוד שמישהו אחר יכול לשחזר? | כל תוכנית |
| **Q6 · Reconciliation** | האם המסמכים תואמים למציאות שנוצרה? | כל תוכנית |

**Q2 חובה** לתוכנית שנוגעת ב**זהות, בכסף, בתאימות או בנתוני משתמש** — כלומר
P1, P3, P6 ותוכניות עתידיות דומות. **הצדקתו עובדתית:** סבב Red Team אחד בפרויקט
הזה הפיל 34 ממצאים, ובהם טענת חפיר שגויה שאף מנגנון פנימי לא תפס.

**Q5 — כלל ההישרדות:** ראיה שקיימת רק בראשו של מי שביצע — אינה ראיה.

## 11. Ownership

| # | הכלל |
|---|---|
| **O1** | **לכל תוכנית בעלים אחד — אדם, לא צוות.** הוא עונה על "האם היא הסתיימה". |

## 12. היחס למסמכים הקיימים

| המסמך | תפקידו | היחס אליו |
|---|---|---|
| **חוקה · זהות · Design Language** | מה Dubiz **היא** | עליונים על הכול. שינוי בהם — לפי כללי התיקון שלהם |
| **Baseline Readiness Audit** | מה **קיים** | **מקור העובדות היחיד.** מתוקן רק במדידה (§7.3) |
| **Release & Store Readiness Audit** | האם ניתן **לשחרר** | משלים את הבסיס; אותם כללי תיקון |
| **Master Program Architecture** | **סדר** הבנייה | מקור התלויות והמקביליות (§9.1) |
| **Program Design Documents** | מה כל תוכנית עושה | תנאי ל-Entry Gate (E1) |
| **המסמך הזה** | **איך עובדים** | אינו מכיל עובדות מערכת ואינו מכיל תכנון. **רק כללים** |

**כלל אי־הכפילות (חוזר):** מסמך זה **אינו משכפל** אף עובדה, פער או תלות. הוא
מצטט במזהה בלבד.

## 12א. ברירת המחדל: ביצוע — נכנס לתוקף 2026-08-18

**שלב התכנון נסגר.** ברירת המחדל של הפרויקט מתהפכת.

| | הייתה | מעכשיו |
|---|---|---|
| **ברירת המחדל** | פער → מסמך → ארכיטקטורה → ממשל → תוכנית | **חסם → פתרון → אימות → סגירת Capability → עדכון לוח** |

### 12א.1 מחזור העבודה החדש — חמישה שלבים

| # | השלב |
|---|---|
| **1** | **שיוך** — לאיזה Capability העבודה שייכת |
| **2** | **קישור** — איזה Release Blocker היא מקדמת (`B#` / `C#` / `X#`). **אין מזהה → אין עבודה** (§9.3) |
| **3** | **ביצוע** |
| **4** | **אימות** — הדגמה, לא הצהרה (G1) |
| **5** | **עדכון** — Product Readiness Dashboard + מצב ה-Release |

### 12א.2 מתי בכל זאת נכתב מסמך

**שלושה מקרים בלבד. כל השאר — ביצוע.**

| # | המקרה | המסמך |
|---|---|---|
| **1** | **פתיחת תוכנית** | Design Doc — תנאי `E1`. **אינו "מסמך יסוד" אלא מסמך תוכנית** |
| **2** | **מדידה שסותרת עובדה מתועדת** | תיקון ל-Baseline לפי §7.3 |
| **3** | **כלל שנכשל בפועל** | תיקון למסמך זה לפי §13 |

> **מסמך יסוד חדש אינו נכתב עוד.** שכבת היסוד שלמה: חוקה · זהות · שפה עיצובית ·
> שני אודיטים · Master Architecture · Governance · שני לוחות.

### 12א.3 מקורות האמת — חלוקה מחייבת

**חידוד קריטי:** הלוח הוא מקור אמת ל**מצב**, ולעולם לא ל**עובדות**.

| השאלה | המקור היחיד |
|---|---|
| **מה מוכן · מה בביצוע · מה חסום** | **Product Readiness Dashboard** |
| **מה קיים במערכת** | **Baseline** — מתוקן **במדידה בלבד** (§7.3) |
| **מה מותר וכיצד עובדים** | **המסמך הזה** |
| **מה הסדר ומה תלוי במה** | **Master Program Architecture** |

> **כלל הברזל:** אחוז בלוח מתעדכן **רק בעקבות שער שנסגר בראיה** — לעולם לא
